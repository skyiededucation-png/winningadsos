# Adtomatic Content Framework

以Performance Marketing Strategist与Content Director的职责执行。把业务资料转成可投放、可筛选目标客户、可交给设计师、可回填结果的内容框架。本文件同时供AI执行、员工培训和MCP App流程设计使用；不代表App已经部署。

本Skill负责策略与内容；`adtomatic-performance-creative`负责视觉概念、排版、生成与局部改图。不要用图片生成Prompt代替内容判断，也不要把完整框架缩成一句社交帖文。

## 1. 总原则、资料权威与内容锁

按 **Business Result > Conversion > Lead Quality > CPL > Creative Aesthetics** 判断取舍。明确希望谁采取什么合格行动，不以便宜询问、免费领取人数或设计满意度代替商业结果。

- 先区分Adtomatic自身获客、客户业务获客、团队招募、旧Lead激活。向Cleaning老板销售获客服务与向住户销售清洁服务，买方与转化事件不同。
- 优先使用最新、适用于该项目的明确用户确认；其次为核实来源；历史资料与模型建议保留状态。不要因为资料较新便覆盖另一项目的批准规则。
- 对每项重要事实记录`scope`、项目、来源、日期、版本、`evidence_status`、`approval_status`与替代关系。证据状态用`user_confirmed`、`source_summary`、`historical`、`proposed`、`needs_verification`。
- Proven Copy、Proven Data、Conversation Core与用户说「保留content」的内容逐块锁定。未经授权不改字、数字、大小写、限定词、Offer、CTA、渠道和触发词；改善建议单列。
- 区分「可审核资料」「初步符合资格」「预约面试」「录用」「激活」，以及「提交申请」「获批」「放款」。不得把前一步写成后一步保证。
- 缺信息时先用现有来源补齐。可以并行完成不依赖缺项的草稿；只询问会改变目标、资格、真实承诺或执行路径的关键问题。未核实的承诺不放进发布文案。
- 用户已授权整理、改写或制作时继续执行；草稿状态不自动要求每一步重新批准。广告发布、对外发送和账户操作另按真实授权处理。

按任务增量执行：新Campaign建立完整Brief；小改沿用已有资料，只检查受影响部分，不重做全部Mining和Hook库存。已有可定位原文可作为父版本；系统版本ID缺失记待补，不阻塞兼容草稿。

## 2. 建立Client Profile与Campaign Brief

先读取当前任务、已批准项目资料和真实反馈。研究市场、竞品或平台现行事实时保留来源与日期；不要把推测包装成客户访谈或实测数据。

| 必填内容 | 要回答的问题 |
| --- | --- |
| Client／业务／产品／地区／语言 | 谁提供什么，服务谁，在哪里沟通和交付？ |
| Business objective | 增加哪种业务结果？为何这轮值得做？ |
| Master Value Proposition | 对哪类人，以什么机制推进什么价值？与已有办法有何实质差异？ |
| Niche／Persona | 哪个细分市场、哪种角色、什么业务阶段与情境？ |
| Final conversation outcome | 聊天希望推进到预约、报价需求、资料提交、申请、面试、试课还是其他事件？ |
| Qualification | 谁适合、谁不适合；哪些条件可以由客户确认，哪些需专业人员判断？ |
| Offer／CTA／Channel | 给什么、条件是什么、去哪里、发送什么、下一步会发生什么？ |
| Mechanism／Sales handoff | AI做什么、团队做什么、怎样接手、哪些资料仍缺？ |
| Evidence／Constraints | 真实案例、可用数字、授权素材、锁定原文、格式与不可承诺事项？ |
| Measurement | 目标事件、目标成本、质量反馈、观察窗口与数据来源是什么？ |

### 2.1 Customer Mining六问

1. 最想要什么具体结果？
2. 现在最烦什么、卡在哪里？
3. 试过什么办法？
4. 为什么仍没解决？可改善的机制机会是什么？
5. 最大顾虑、反对理由或不行动原因是什么？
6. 什么结果、信息或安排会让他愿意预约或推进下一步？

即使研究了痛点，Desire广告也不必写痛点。无法访问真实客户资料时，把答案标为待验证洞察，不虚构访谈。

### 2.2 价值定位与转化路径

Adtomatic自身业务在没有替代定位时使用以下已确认核心价值；不套到客户自己的产品：

> Adtomatic AI 把广告获客、客户筛选、资料收集、持续跟进连起来，让花钱买来的询问，更有机会变成可以谈生意的预约、报价需求和申请。

不要缩成「自动回复机器人」或只卖「免费搭建系统」。区分长期价值定位、短期Offer与本次下一步。内容顺序通常为 **Desired Outcome → New Mechanism → Offer**，避免每段重复免费优惠。

每轮优先选一个明确Niche；如需探索，可先建议2–4个候选再选定。用户已批准跨行业Campaign时保留范围；通用获客八框架与商业融资的已批准宽受众属于具体项目例外。

定义路径为「看到广告 → 询问 → 资格与需求确认 → 必要资料 → 合格下一步 → 团队接手 → 最终结果」，按实际业务调整，不强迫所有项目都以预约结束。

## 3. 内容骨架与模型选择

### 3.1 五步内容框架

**给谁看 → 现在的问题与欲望 → 价值点 → 能帮什么 → CTA＋Offer。**

「给谁看」负责识别；「问题与欲望」负责行动动机；「价值点」负责为什么值得；「能帮什么」负责具体动作与机制；「CTA＋Offer」负责清楚下一步。五项是思考检查，不要求把栏目名称印在广告上。

### 3.2 Funnel Marketing四层

1. **第一层：给谁看。** Niche、Persona、业务阶段或资格。
2. **第二层：Hook＋Desire＋Number Outcome。** 先让目标认出想要的结果；数字仅在有批准依据时使用。
3. **第三层：怎样做＋机制价值。** MEAT说明服务如何推动结果，而非堆功能。
4. **第四层：Offer＋CTA。** 写清行动、渠道、关键词、得到什么与必要条件。

### 3.3 Alex Hormozi Hook／MEAT／CTA

- **Hook**：一个主要动机、情境或结果；不是把全部功能塞进标题。
- **MEAT**：连接客户情境、机制与价值。Desire内容可用「想要的结果 → 机制 → 下一步」；Pain内容可用「问题 → 机制 → 结果」，不强迫所有广告先制造痛苦。
- **Offer＋CTA**：给行动理由与执行路径。Offer通常集中在尾部区块，不靠重复免费掩盖价值定位。
- 用户要更「满」时，增加有信息量的MEAT，例如确认哪些需求、收什么资料、怎样交给Sales；不要填空洞形容词。原文已锁定时只提出附加建议，不擅自改进图片文字。

### 3.4 SLAP用于广告正文

严格按 **Stop → Look → Act → Purchase** 组织Primary Text：Stop抓住目标注意；Look让他看见相关欲望、机制与价值；Act讲清行动；Purchase承接Offer与更深的合作意愿。Lead广告里的Purchase不等于必须即时付款，不虚构已经成交。

用户要SLAP时交付完整结构；同时另列Meta Headline与Description。SLAP制作标签默认不印进消费者看到的正文。它与图内Hook／MEAT／CTA属于不同交付层，不把其中一套当作另一套已完成。

## 4. Angle、心理动机与独立假设

先明确本轮是 **Pain、Desire还是Person／Persona**。三者可以围绕同一业务，但应有各自的主张与假设；不要同一句换个形容词就算三套。

- Pain：哪个具体阻碍值得现在处理？
- Desire：希望怎样经营、怎样工作、获得什么状态？可直接从心理动机切入，无须补痛点。
- Person：哪类角色、阶段或情境的人觉得「这是我」？不是只换一张人物照片。

需要探索时可内部提出4–6个Angles，再按任务数量选择；这属于可调工作方法，不强制每次输出50条或多张图。旧的Problem／Benefit／How-to／Proof／Before–After／Objection／Comparison／Mistake／Offer／Curiosity十分类不作为当前默认分类；仅在用户明确启用时使用。

| 已确认的八个Desire动机 | 业务含义 | 观察的合格行动 |
| --- | --- | --- |
| 扩张意愿 | 生意进入下一阶段 | 愿意讨论扩张目标与落实安排 |
| 掌控感 | 有意向客户有清楚下一步 | 预约、报价资料或申请推进 |
| 时间自主 | 老板专注商谈，流程承接重复处理 | 可交给Sales的明确需求 |
| 成交准备 | Sales接手前有需求与资料 | 接手质量、方案讨论 |
| 资源增值 | 从已有Lead重新确认机会 | 有效回复、继续商谈意愿 |
| 执行确定感 | 团队协助规划和搭建 | 准备落实方案的老板预约 |
| 合作期待 | 有兴趣的人愿意行动 | 愿意约、愿意交资料 |
| 行动承诺 | 准备扩大获客并讨论执行 | 带着目标与团队安排讨论 |

动机库是选题来源，不是每个客户必须套用的八张模板。每个独立内容概念回答：**给谁、想要什么、怎样帮助、为什么愿意行动、预计带来什么合格结果、用什么验证。**

假设句型：**对[Persona]，以[Angle／Desire]配合[机制与主张]，预计提高[合格行动]；通过[事件口径、成本与Sales反馈]验证。**

## 5. Hook Inventory、MEAT与内部筛选

需要批量探索时按 **Angle → 最多50个Hooks → 选中Hook → 1–3个MEAT与1–3个CTA候选** 进行。50是库存上限与历史SOP方法，不等于一次必须交付50个、不等于50条都制作投放；具体数量服从任务。不要将所有候选塞进一张静态广告。

Hook需要受众认得自己、业务结果明确、具体且能形成清楚视觉。不要只有「AI帮你成长」或泛称所有SME老板；已经批准的跨行业Hook用行业区和MEAT补足识别。

可启用产品规格记录的内部Hook评分：每项0–5、总分30。记录评分理由与`rubric_version`，团队可以调整；不是平台算法、效果预测或用户已经逐项确认的永久规则。

| 评分维度 | 评估内容 |
| --- | --- |
| Audience Recognition | 目标是否认得自身角色与情境？ |
| Motivation Strength | Pain批次评痛点强度；Desire批次评欲望与心理动机强度，不硬加Pain |
| Curiosity | 是否有相关且有信息量的继续阅读理由？ |
| Business Outcome | 是否指向业务结果，而非只讲AI？ |
| Specificity | 情境、机制、结果是否具体且有依据？ |
| Visual Potential | 能否转成容易理解的广告表达？ |

沿用该内部版本时，≥24为Production候选、20–23为Reserve、<20为Reject候选；它只辅助选内容，不替代事实检查、人工判断或上线授权。锁定文案不因分数低就被自动改写。

选中Hook后，用MEAT回答「先确认什么 → 怎样处理 → 怎样推进 → 谁接手」。按任务长度精简，避免夸张的全自动获批、自动成交或保证结果。CTA候选必须与同一批准Offer兼容，不能为测试擅自增加优惠。

## 6. 数字、Offer、资格与渠道

- 区分**目标数字、规划容量、真实成果、限量名额、服务时长**；保留单位、周期、适用条件与证据。
- 「月度目标10–20个预约」不是「保证下月新增20单」；「只限10位老板」不是「保证获得10位客户」。
- 没有批准数字时可以写非数字Hook，或在内部Brief列「数字待确认」，不能为了Number Outcome现场编数。
- Reno某个已批准Desire批次的「15++」只属于该批次。Recruitment的数字与Cleaning预约数字互不套用。
- 限量、免费时长、价格、利率、到账时效、审批条件必须有当前依据；用户已锁定的历史文案仍保留来源，出现冲突时不自动标成可发布。

| 项目范围 | 批准的Offer／CTA／渠道 | 防止串用 |
| --- | --- | --- |
| 通用获客八框架01–08 | 免费搭建AI获客系统＋免费1个月服务；发送「行业＋地区」，预约了解获客与跟进方案 | 不改成只领免费Bot；保留名额资格 |
| Recruitment | 点击 Send Message 发送「新人」；免费搭建 AI 新人Recruitment System | 免费1个月服务已取消，不恢复 |
| Cleaning获客五框架 | 点击 Send Message 发送「清洁获客」；免费搭建 AI 清洁获客系统 | 不套「新人」，不加免费1个月 |
| AS Badminton | 按课程／地区／语言批准版本进入WhatsApp | 不套Adtomatic Offer或Send Message；团课与1-to-1分开 |
| 商业融资／其他客户 | 该客户当前批准CTA、资格与真实Offer | 不套Agency免费系统或招聘承诺 |

写CTA时一次核对：动作、入口、发送词、收到什么、谁适合、下一步。Send Message、WhatsApp、表单、预约链接不是可以随意互换的同义词。

通用八框架的批准CTA没有单独写明入口：沿用该Campaign已有渠道；未提供则内部记录`channel=未提供`，保留CTA原文，不擅自补Send Message或WhatsApp。缺入口不阻塞内容整理；需要配置或发布时再解决依赖项。

只收集推进下一步必要的资料。把联系结果、资格与销售阶段分开记录；**MIA／未回复不自动等于不合格或没需求**。不合格原因需区分误点、无需求、条件不符、重复与其他。

## 7. 标准交付卡：Marketing Content与设计交接

用户要5个框架就交5张完整内容卡；用户要「附加4个」时保留原有1个，加4个后整理为5个。多个行业分别计数，不把总数当作每行业数量。

```text
[Creative ID｜内容主题／Angle]
业务目标：
受众／Niche／Persona／地区／语言：
转化结果＋资格：
主Hook：
适合：[跨行业时列全；单行业按需要呈现]
MEAT：[机制＋价值＋下一步]
Offer：[完整批准条件]
CTA：[动作＋渠道＋触发词＋得到什么]
限定条件／数字性质：
Test hypothesis：
Evidence／待确认：
设计交接：[主视觉应说明什么、主次字级、比例、限制]
```

制作字段不自动印在广告图上。用户只要上图内容时，交Hook、适合行业、MEAT、Offer、CTA与限定条件，其他字段作为内部记录。用户明确「保留content」时不附带改写锁定正文。

全文文案中的`\n`仅标记批准分行，输出给设计或消费者时转换为真实换行，不渲染反斜线字符。内容卡完成不等于可立即发布；渠道、当前Offer依据、素材与设计检查按各阶段记录。

设计交接顺序通常为 **大Hook＋相关主视觉 → 中间「适合：」行业区 → 可读MEAT → Offer＋CTA → 资格／名额**；这是阅读顺序，不是必须切成几条固定色块。

行业名称与MEAT都需要在手机上看得到，不能只放大「适合：」标签。内容过长先讨论重排或经授权精简，不把关键条件藏成小字。本会话已确认系列静态图使用3:4，其他客户按各自Brief；记录比例所属Campaign与版本，产品旧规格的4:5不覆盖本轮明确3:4。

概念视觉应支持买方身份与机制，不能把向老板卖系统误画成向住户卖清洁、向买家卖房或向求职者招工。人物限制按对应任务、Campaign与版本记录，不永久扩展到所有客户。

与设计师交接时回答Who、Desire、Mechanism、Visual、First Read、Hypothesis六问：给谁、要什么、怎样做、画什么、先读什么、验证什么。可用颜色、人物、文字、物件、环境、情绪检查表达是否匹配；这六项是创意观察维度，不是已证实的Meta算法规则。

## 8. Meta投放文字独立交付

需要完整投放包时，按每个Creative ID另列：**图内原文、Primary Text、Headline、Description**；不把Headline／Description混在正文里声称全部完成。

- Primary Text使用请求的模型，SLAP或Hook／MEAT／CTA均需完整。不能以一段长社交贴替代Performance广告内容。
- Headline用直接、相关的业务或行业关键词，避免只写含糊情绪词。
- Description补Niche、Persona、地区、资格或下一步的有用信息；自然表达，不堆关键词，也不重复整个Headline。
- 使用自然的马来西亚中文、英文或马来文；按地区与群体本地化，不用同一语言自动覆盖所有地区。保留批准的Lead、Sales、Property等词。
- Emoji只在帮助识别、节奏或行动时使用；不靠无关符号制造信息量。字数限制按当前渠道、字段和真实工具验证，不把某个模板的80字限制套到所有文案。
- WhatsApp预填文字与自动回复属于Conversation交接，记录触发词、必要问题与接手条件，不擅自改已证明有效的Conversation Core。

## 13. 内容QA、Lead反馈与学习

先过事实与范围硬条件：原文完整、Offer与渠道一致、数字性质准确、资格清楚、没有跨项目串用、没有伪造证据。硬条件失败不能用高评分抵消。

再做七项QA：①3秒内理解主张；②目标受众认得自己；③Hook讲业务欲望／结果／问题而非只有AI；④机制清楚；⑤CTA明确；⑥手机Feed下Hook、行业、MEAT与条件可读；⑦有明确测试假设。内容阶段第⑥项可标待设计检查，未看实际图不能宣称已通过。

收到反馈先诊断：低点击可能与识别或主张有关；询问多但质量低要查受众、Offer与资格；有意向但未推进要查资料、安排、Conversation与Sales接手；MIA单独记录。不要一律归咎Hook或把所有未回复算垃圾Lead。

回填Spend、Leads、CPL、Qualified Leads、Sales接手、预约／报价／申请推进、到场与付费结果，使用相同事件口径与可比较窗口。评估合格行动成本和业务结果，再看CPL。样本不足时保持未验证，不设所有项目统一三天淘汰或RM10 CPL标准。

Winner根据该Campaign目标、成本、质量与下游结果综合判定；申请型项目不强迫用面试或预约作为唯一条件。复盘记录哪些Angle／Hook／机制有效、对谁有效、证据多强；不能把相关性写成单变量因果。

## 15. 员工执行、练习与覆盖检查

员工流程：**业务资料 → VP与目标 → Niche／Persona → Customer Mining → 转化与资格 → Angle＋假设 → Hook库存与选择 → MEAT／Offer／CTA → 内容QA → Meta文案与设计交接 → 反馈学习**。用户只要框架时停在已完成的内容交付，不擅自发布。

1. 练习Desire：为准备扩张的老板做内容，直接表达心理动机；验收不强加Pain，不只卖免费Bot。
2. 练习Offer隔离：分别整理Recruitment、Cleaning与通用获客；逐字核对触发词与免费月份，不能互相抄CTA。
3. 练习数字：说明10–20预约目标、10位限额与真实已完成预约的区别；不把15++复制到所有行业。
4. 练习交付：同一概念交图内文案、SLAP Primary Text、Headline、Description；陌生同事能说出给谁、怎样做、下一步。
5. 练习局部修改：用户只换CTA，保留其余字段；用父版本差异检查验证。
6. 练习数据：CPL低但合格率低、Lead未回复、面试已约未出席分别诊断，不统一写「广告赢了」或「Lead不合格」。

交付前逐项覆盖：目标／VP、Niche／Persona、心理动机、转化与资格、Hook、MEAT机制价值、Offer、CTA渠道与触发词、数字与条件、独立假设、证据状态、数量与ID、Meta字段（若要求）、Design Brief（若要求）、锁定与父版本。
